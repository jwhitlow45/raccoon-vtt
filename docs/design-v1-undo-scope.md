## 1. The owner's words and the boundary

The project owner's notes of 2026-10-29:

- "undoing damage applied from save in the dice panel should revert the dice panel state back to the state prior to the damage being applied and allow DM to re-roll the save/modify DC. just once the damage/effects are applied that panel is unchangable"
- "review of what undo should and should not do. for example, undoing a stat block modification is a bit weird. just general pass to ensure this doesn't result in accidentally undoing stat changes without players noticing. obviously damage and movement should be part of this but the line is blurry so I want you to figure out where that line should be"

**Ordinary Undo takes back a table action or a direct board edit. Setup Undo takes back a saved definition or configuration.** Damage, movement, conditions, turns, shapes, doors, fog and building on the board stay in ordinary Undo. Stat blocks, character sheets, saved encounters, scene configuration and room settings leave it. The same operation has the same scope during a fight and during preparation. Starting a fight does not change the meaning of Undo.

Direct board editing is the deliberate exception to "play versus setup": painting a floor or erasing a wall needs the same immediate correction as drawing or moving a token. Saving a creature's abilities changes what future actions mean. It belongs in a history the DM deliberately opens. Labels and advance feedback make the distinction visible.

Setup keeps a separate, guarded Undo and Redo for the DM. It is not a backup or a revision browser. Players retain today's move, resize and drawing stack, plus specific correction controls such as Restore and the re-sync dialog's Undo. No new player permission to restore a character or a monster is introduced.

## 2. Today's implementation, and the complete inventory

`server/rooms/actor.ts` records an op only when `UndoStacks.records` accepts it **and** the reducer returned an inverse. `server/rooms/undo.ts` accepts every DM op except `sys.*`, `roll.change`, `cast.close` and thumbnail-only `scene.update`. `shared/reducer/tx.ts` excludes log entries and bookkeeping from inverses. Consequently a phrase in `undoLabels.ts` does not prove that an op enters a stack.

Stacks belong to a member, shared by that member's devices, with 50 entries per direction in server memory. Restarting or unloading the room loses them. Only the resolved `sys.restore` is durable. Guards prevent replacing values changed since, dependencies prevent stranded references, and an oversized inverse clears the affected history rather than reaching past the action. Gesture merging is consecutive and guarded.

The tables list every client op family in `shared/protocol.ts` at the checked commit. **D** means today's DM stack when there is an inverse. **P** means today's player stack, subject to permissions. **Play**, **Setup** and **None** are the proposed DM destinations. ## 3. Exact classification and protection from hidden setup changes

One exhaustive shared `undoScope(op, before)` returns `play`, `setup` or `none`. The server uses it after validation, with the actually accepted op. The client uses the same rule for wording. A compile-time exhaustive switch and a schema-derived inventory test require every new op to choose a scope. A new patch field defaults to Setup until explicitly classified. The client cannot label an arbitrary stat edit as Play.

- `token.update`: Play only when every top-level field is in `sceneId`, `x`, `y`, `elevation`, `rotation`, `size`, `w`, `h`, `visibility`, `light`, `companionReaction`, or a permitted play `actor` patch below. Moving a token between scenes is play. A token's name, `number`, art, ownership, kind, disposition, layer, locking, public-name rules, HP disclosure, sight sharing, fog exemption, companion link, notes, range rings and physical height are Setup. `token.updateMany` follows the same field rule on its smaller schema.
- Actor patches inside `token.update` or `character.update`: current/temporary HP alone are Play. Maximum HP, AC, speeds, initiative modifiers, senses, sheet links, notes, stat-block links and legendary capacities are Setup. The HP section's separate `actor.hp` Set, maximum included, is Play even when used for initial setup. This explicit action boundary supports Aid and Life Drain without guessing intent. Legacy hand edits of spent legendary counts are Play only if every maximum equals the existing value and nothing else changes. Current UI uses `actor.use` instead.
- Taking or ending a character's shape is Play: an actor-only patch of the exact `shapePatch`/`END_SHAPE` structure in `client/features/pcstats/shape.ts`, on a character actor or its reference token. It changes `srdId`, optionally `wildShape`, the form's AC/speeds and temporary HP. It must not carry sheet fields or HP maximum. Attaching a block to an inline monster is Setup. This structural exception does not make a plain AC edit Play.
- `character.update`: Play only for those actor-only HP or shape patches. All other fields are Setup, including default size. Resizing a placed token is Play instead. A re-sync stays wholly Setup, including its HP clamp and resource counts.
- `scene.update`: thumbnail-only is None. `suggestedView` alone is Play. A `vision`-only patch is Play when only light changes: its required `on` must equal the current effective value, and `perPlayer`, if sent, must equal the current effective value. The current schema requires both `on` and `light`, so classification compares those values rather than demanding an impossible light-only payload. Everything else is Setup, including vision on/off, fog mode, per-player sight and phase definitions. A patch combining live and configuration fields is wholly Setup.
- An empty or no-effect op creates no entry, except a successful tracked outcome: its lifecycle-only step must undo the page's applied state even with no entity inverse (section 6). The reducer's real inverse, including cascades, follows the operation's one scope. Never divide an already applied inverse between histories or guess scope from the screen open at Undo time.

Mixed patches and a deliberate mixed gesture go wholly to Setup. A DM producer knows its gesture before sending its first part and declares `groupScope: setup` alongside its group id when any part is Setup. This may promote Play parts into Setup, never demote a Setup part into Play. The server fixes the group's scope at its first accepted part and refuses a later contradictory part before applying it. It never relocates an already offered or undone entry. Preserve consecutive, guarded merging and existing size/interruption splits. Each retained step restores atomically. Current producers keep ordinary HP controls separate from sheet saves and declare a grid detection's shape and grid as Setup from the first part.

### 3.1 Blocked steps and DM movement

Inline monster actors live inside their token entity, and PC actors inside their character entity. Most DM restores keep whole-entity guards. A sheet save followed by a hit cannot safely restore the old character wholesale. A DM restore **peeks and validates before deciding whether to retain or consume the step**. For a successful restore, one synchronous handling mutates the stack only after a successful reduce. Publish history heads after commit. There is no stack rollback: commits retry while the room is open, and closing abandons its memory-only stacks. Player state-conflict and trapped-move drops stay as today. For either role, read-only, quota, replay-failed and rate refusals keep both stacks unchanged: these are admission failures, not state conflicts.

**For state conflicts, keep a refused DM Undo or Redo when attributable to this member's entries on the other scope's Undo or Redo stack.** Compare conflicting values, not just keys, with the candidate entry's after-values. Store attribution values/poses for both directions, oriented to the action that created the entry: a Redo entry's after-state is the state produced by Undo. Name the newest blocker and its required direction/scope: "Undo the play step first: damaging Bree", "Undo the setup step first: changing Goblin 2's AC", or "Redo the setup step first: changing Bree's stat block". If buried, say "Undo the play steps through damaging Bree first" (likewise for Redo). Never jump. External/player-answer/unrecorded conflicts refuse with today's changed-since reason and drop the step, with no restore or opposite entry. Other state failures without attribution also drop. Head mismatches, pending asset lookup and unanswered/canceled/stale forget confirmations consume nothing, section 4.1.

Only steps retained for state conflicts offer **Review step**, with Retry and **Discard this step**. Discard asks "Discard this undo step? The game stays as it is." It removes only that retained expected head in the named direction/scope, creates no inverse or player notice, and cannot remove a replacement head. Retry rechecks attribution, so a later external conflict can cause the ordinary refusal/drop. Save-page asks and their replacements record no step at all, section 5.3.

DM Play movement uses a new adapter, not the player's `poseRestore`, which skips encounter entries and refuses other entity kinds. For moves, facing/elevation, counted legs, attach/detach, resizes and position-only scene transfers, retain before/after poses and a per-token eligibility mark. Ignoring revision/bookkeeping, an existing token changed only in `sceneId`, `x`, `y`, `elevation`, `rotation`, `size`, `w`, `h`, `squeeze`, `path` and `attached` qualifies. Compare its current complete pose with the saved after-pose, then copy only those pose fields from before onto its current token, deleting optional pose fields absent before, and guard that constructed restore with the current whole-token hash. Later AC, HP, names or art survive. Attribute a pose-mismatch refusal by comparing the current pose with the other-scope entry's after-pose on either stack, even for a mixed Setup entry. Missing tokens use the same value-attribution rule.

Keep every other inverse entry with its original whole-value guard: encounter changes, attached areas, trap doors/lights/pits, actor changes, creations/deletions, and a token whose move also changed non-pose state. Restore these together with adapted token entries, or nothing. Never omit a non-token entry or a trap side effect to make a move succeed. Preserve this distinction through gesture merging and Redo, recomputing poses from the successful restore. The adapter preserves current setup values but does not merge arbitrary actor fields. Thus moving Goblin 2, fixing its AC, then Undo moves it back with the new AC. Saving Bree's block, hitting her, then Undo setup keeps its refused step until Play Undo removes the hit. Damage followed by a stat edit requires Setup Undo before the older whole damage Undo. The narrower HP Log correction remains available under its existing checks.

## 4. Controls, histories and visible feedback

### 4.1 Ordinary and setup history

- Top-bar buttons keep the visible words **Undo** and **Redo**. Their descriptions become "Undo your last play or board change" and "Redo your last play or board change". Existing shortcuts, Draw and Builder use this scope. Empty Play never falls back to Setup.
- Menu gains **Setup history**, DM only. Its sheet shows the latest setup step's phrase and **Undo setup**, then the latest redo phrase and **Redo setup**. It is deliberately not a second pair of unlabeled arrows in the top bar. No new global shortcut. While this sheet has focus, Ctrl/Cmd+Z and Shift+Z invoke its named setup actions, except in text fields.
- Setup editors say after a successful DM save: "Saved. Undo in Setup history." Re-sync keeps its own immediate Undo in the done state for players and DMs. Its forward save and explicit inverse are Setup for the DM, never Play. **Undo setup after the dialog's Undo reapplies the sync**, which is allowed and named explicitly. Ordinary toolbar Undo cannot do that.
- The server sends each member private head ids, safe labels and depths for each available scope/direction. Every stack Undo and Redo, Play included, requires `head`, the opaque id captured from the displayed intended head. Change the id on merge, replacement or transfer to the opposite stack, and never reuse it across room loads. Check it before asset lookup/forget preflight and again before mutation after any wait. A mismatch says "Play history changed. Check the next change." or "Setup history changed. Check the next change." It changes neither stack and never takes the replacement entry.
- A fresh activation waits for the authoritative summary covering the current confirmed view and preceding command's ack, then captures its head before queueing. Never send a locally stale head. A double activation is only a second pointer tap on the same control within the platform double-click interval: it reuses the first activation/id, even across its ack, and is ignored if that id was consumed. Ignore `keydown` with `event.repeat`. Separate keydowns are deliberate activations and wait for a covering summary. Later remote changes still meet the server head check. Token-bar `undo.of` adds its origin check. HP Log correction uses `log`, not a head.
- Show the next Play phrase in the top buttons' tooltip and accessible description when known. Success says "Undid moving Goblin 2." or "Undid setup: changing Bree's stat block." Redo is equally explicit. Before an authoritative summary, stack actions wait with "Loading undo history…". A bare legacy stack command is refused with "Reload to use Undo", section 7.
- Preserve `#forgetAnswered` for **both** scopes and directions, using the final constructed restore, including DM pose adaptation. Go ahead carries both the original forget-question sequence (`forget`) and expected head id. Recheck the pair and current memory preflight before applying. A stale yes forgets nothing and leaves the step. Setup Undo/Redo are never exempt from this question.

DMs have Play and Setup stack pairs, each 50 entries per direction, memory-only and shared across that member's devices. A new accepted action clears only its own classified scope's Redo. No-effect actions without a lifecycle entry, `none` actions and bookkeeping clear neither. A Play move therefore preserves Setup Redo, which still checks current guards. Undo/Redo move only their own entry. Players keep today's single pair and clear Redo only when `UndoStacks.push` records an entry. Other members' actions do not eagerly clear histories, but their conflicts drop a step when its restore is attempted. An oversized entry clears its scope's Undo and says the change cannot be undone. Section 3.1 defines the narrow retained-refusal case.

### 4.2 Tell players what affected them

A DM undo or redo produces **at most one player notice per gesture**, also retained in that player's Log, only for restored gameplay state below or the position of a token that player owns. Include Actor HP, life/death saves, combat numbers, conditions/effects, shapes and spent uses. Compare gameplay **Character.stats**, including abilities, save/skill proficiencies, adjustments, defenses, Evasion and mechanical roll definitions/formulas, plus **level, knownForms and resources**. Also compare the owner's **CompanionBlock** definition fields, all except name and images, including action/trait text. Companion changes can leave Actor and Character identical. Example: "The DM undid a play change." For a sheet change: "The DM undid a setup change to Bree." Cosmetic text/notes outside those gameplay definitions, names, images, walls, fog, drawings and other people's token positions produce no notice. `monster.update` and savedEncounter changes need none: players never receive those definitions. All DMs get the exact label privately. Ordinary sheet saves are outside this notice change.

Compute recipients on the server by comparing only those allowed fields in each viewer's semantic projected before/after state. Ignore revisions, timestamps, logs, sync/source provenance and private bookkeeping. Private actor, character or companion stats reach only owners who actually receive them. Hidden movement sends no public notice. Deduplicate all targets in a gesture into one notice per viewer. A DM view preview obeys the selected player's audience, not the DM's.

Freeze recipients and any allowed name when writing the event, then intersect with permission to read it now, using the existing audience rings and private parts. Do not broadcast the DM's label, ids, DC, hidden targets, damage totals, counts of affected creatures or the reason a guard failed. Generic words suffice where no safe name exists. No change visible to a player means no notice, including no otherwise empty event or event-derived counter. Announce once through the existing polite status/toast path, without opening a dialog or stealing focus.

An individual HP Log undo keeps its existing projected take-back line rather than adding a duplicate generic notice. A full outcome Undo writes a notice only if those allowed fields change for that viewer. Lifecycle-only Undo/Redo writes none to players. Old rolls, HP and effect lines remain historical facts. Redo never duplicates the original roll.

## 5. Reopening the group save

### 5.1 Identity, not a guess from HP or the log

Today `chain.apply` sends request closes, then one `actor.outcome` with a receipt tag in `plan`. `applySettled` locks the local page permanently. `castSeen` returns immediately for an applied page, even if Undo restored its ask. Its draft is in this tab's `sessionStorage`, not shared room data. A recharge action's automatic Use is currently a separate op after Apply.

**Reopen only after a successful whole restore of that page's current outcome entry.** The scope can be Play Undo from the top bar, a shortcut or the same member's other device. It need not be the device that applied. Track the outcome explicitly through its UndoEntry and RedoEntry. A failed restore, undoing a request close, Previous, a manually equal HP value, an effect removed by hand, or a row's HP Log undo never proves the outcome was undone.

This deliberately excludes partial corrections. One target's HP back while three conditions or another target's damage remain is not a page ready to Apply again. Even undoing every HP line separately does not count. The page stays locked, and the DM corrects the remaining values explicitly or starts a new group save. Do not offer Apply that could silently double the effects.

### 5.2 What returns on this device

Just before Apply sends anything, retain a versioned `beforeApply` checkpoint in the local draft. It contains the frozen rows, source and scene, test, DC, typed totals and marks, overrides, save visibility switches, outcome form, chosen damage result and references to completed rolls. It holds no pending command queue. A No save page returns to its previous editable phase. Other pages return to **rolled**, with the same selected creatures and their previous results, not a live selection that may now be elsewhere.

When an authoritative outcome status changes to undone, restore that checkpoint, clear the old plan and apply flags, and show: **"Outcome undone. Change the DC, roll again, or apply again."** A DC edit rejudges numeric totals and preserves explicit pass/fail/resist marks, matching today's rule. The damage total stays until the DM explicitly rolls it again. Reopening itself sends no rolls, requests, damage, effects or resource spending.

Add **Roll saves again** on the reopened page, with per-row Roll again and Ask again for the corresponding server and player rows. Successful rows are eligible here, unlike today's failure-only `rollAgain`. Rerolling the same test keeps frozen targets and bonuses selected for that new roll. Changing test, targets or source uses **Start over**, with confirmation when results would be replaced. It does not apply anything.

Roll again clears only the selected row's old result and manual pass/fail/resist mark before requesting a fresh result. Ask again marks rows pending but keeps old results and request references until acceptance, then clears the selected results. Refusal reconciles current answers without losing them, section 5.3. Typed rows stay typed unless explicitly changed. Every reroll uses a new dice tag, and every new request uses a fresh id. Its note says "Fireball: save again" using the public name, never a hidden trap name. The original result and its original DC remain in the log. A new DC on the page does not rewrite those historical rolls or a closed request. Fresh asks carry the revised DC and current disclosure switches.

The reopened page rebuilds its next plan from current creature state. It does not reuse old effect ids, frozen damage reductions, a spent Resistance, missing creatures or a stale target's ownership. Gone rows stay marked and excluded as today. Off-scene or missing-scene pages cannot apply until their scene is available. The checkpoint restores choices, not the world's previous state a second time.

### 5.3 Repeated outcomes, Redo and requests

One page has at most one applied outcome at a time: Apply A, Undo A, edit or reroll, Apply B. B has a new plan id and its own pre-Apply checkpoint. Undo B restores B's checkpoint, not the first version of the page. Only the latest attempt is editable. Starting a separate group save creates a different page identity. One group's outcome is never split into several partially applied ops to fit a limit.

Redo A while its page is reopened locks it again and says "Outcome restored. Undo it before changing this save." It sends no dice or Apply. Keep any newer local draft edits separately rather than silently deleting typed work. After Undo A again, restore the pre-Apply checkpoint and offer **Resume your edits** for that separately kept draft. Applying B clears Redo A and advances the page identity's revision. A delayed Undo/Redo or receipt for A cannot change B's phase or apply A again. Merely editing the local DC does not clear server Redo.

The save page's own `roll.ask`, including Ask again replacements, and its automatic `roll.close` ops carry a DM-only `reason: savePage` and **record no Undo step**, in either scope. Their scope is None, so they also preserve Redo. The page manages these requests through Discard, Ask again and the request controls. Explicit request controls outside this automatic path remain Play. Apply's closes stay separate commands before the outcome, so its inverse never contains them. After players answer, Apply, Undo, the next deliberate Undo reaches the Play step before the page's asks. The checkpoint keeps old answers while treating those request ids as closed, even though captured before closing them. Losing a close's ack does not cause automatic resending of Apply.

Ask again retires still-open old requests referenced by selected rows, including one restored by an earlier explicit Undo. Add a DM-only `replaces: [{ id, expectHash }]` to `roll.ask`, at most `LIMITS.openRollsPerRoom` (20) unique ids. Capture `guardHash(keys.roll(id), request)` from each whole request when preparing the replacement. Before any write, require every request to exist and its current hash to match. Use the same `guardHash` as restore guards, excluding `rev`. A revision alone is unsafe: `Tx.put` resets it to 1 when restoring a deleted request. Close matched requests and create the fresh request atomically, validate capacity after retirement, and mark retired writes as Tx bookkeeping. Carry only other unanswered rows from a shared request. Partition by old request within `LIMITS.rollTargets` (50), never retiring one whose waiting rows cannot fit. These replacement asks also make no Undo step.

If a player answers a carried row between preparation and acceptance, its request value hash changes. Closing and undoing that close can reset the revision but does not erase the answer from the hash. Refuse the stale replacement with **nothing changed**, keep old references, reconcile and show the new answer, then let the DM retry explicitly. Rebuild the carried set from that current state, excluding newly answered unselected rows and retaining their answers on the page. Do not copy answers into a fresh request or automatically retry. Only after acceptance switch to the new ids and ignore late answers from superseded ids. No old/replacement pair becomes live together.

A tracked Apply folds the automatic recharge `actor.use` into an optional, validated recharge-use part of `actor.outcome`. Use the same `ifReady` rule and quiet audience as today. Its mark and effects commit or refuse together, and Undo returns only a use this Apply actually spent. This is required for "one Apply, one Undo": an extra automatic Use must not sit above the outcome or make reopening spend again. Explicit Use outside the page remains separate. Roll requests still close before the outcome, as today.

### 5.4 A save ask or trap that closed

- If Apply closed its player's save ask, the full inverse restores that same ask atomically with damage/effects and the status. Its caster sees the ask waiting again, plus a correction notice only if section 4.2's gameplay/own-position fields changed. The DM page can resolve that ask again once. This retains the existing outcome exception to final Dismiss.
- If the player withdrew or a DM dismissed the ask before Apply, the page had already become a plain group save. Undo restores that plain checkpoint and never recreates the closed ask. **Close the ask** with nothing to apply remains final and has no outcome to reopen.
- If another device resolved the ask, this device's stale Apply remains blocked. If that resolution is undone, its existing unapplied page can return to the waiting ask under today's `castSeen` rule. It never claims to hold the other device's damage choices.
- A trap outcome restores its exact `trapId` and occurrence `due`, not a new springing. The trap card can return only if the whole guarded restore succeeds. A newer occurrence, a changed rig or a deleted trap must not be overwritten or silently replaced with a plain save. A refusal leaves the page locked. The page's reroll does not run the trap's doors, pit, reveal or other actions again.

### 5.5 Other devices, closed pages and missing history

All DM devices receive the authoritative status. Only a device retaining the matching page and checkpoint restores those exact choices. Another DM device with its own page for the same ask sees the ask restored and can continue or open it normally. A device with no draft gets the correction in the Log and the restored ask/trap card where applicable. It does not manufacture another device's draft. Done, Discard, replacing the page or clearing this tab's storage still discards the local draft. Undo does not pop an old panel open.

Players never receive the DM checkpoint, page identity, status ledger or plan. Their HP/effects update through normal projection. A restored save ask is shown to its authorized caster as today. Old roll-request cards stay closed until explicitly reopened or freshly asked. An applied page that loses contact stays locked. On reconnect or reload, read authoritative status before enabling Apply, even if a cached receipt says committed. A receipt proves the original commit, not whether it was later undone.

If status or checkpoint is missing, say **"This save's outcome cannot be checked. Start a new group save to continue."** Keep the page locked. A missing record is never interpreted as undone. Server restart loses Undo history but retains the status of already applied or undone pages. A retained undone draft can still be edited and reapplied while its status is retained.

## 6. Stored contract, limits and replay

Store only outcome lifecycle metadata on the server, not a second copy of the DM's draft. Introduce optional `RoomState.saveOutcomes`, absent meaning empty, keyed by a tracking id assigned on the page's first Apply. That id is the first plan's UUIDv7, separate from the local draft's existing id. One record has `memberId`, latest `plan`, monotonic `revision`, `state: applied | undone`, first-Apply time and last-change sequence. It is DM-only and at most 512 UTF-8 bytes per record.

- `actor.outcome` gains optional `page: { id, expectRevision }`. The first Apply uses its own plan id and revision 0, and must create a missing record. Further Applies require that exact record, author member, revision and `undone` state. A successful Apply advances revision and stores its plan. Check this before changing any target. Refusal changes neither the record nor game state.
- First creation requires the tracking UUID's time to be no older than the existing maximum pending-op age of 12 hours, with at most five minutes of clock lead. Move `MAX_OP_AGE_MS` from `client/state/store.ts` to shared code before this new server check imports it, and have the client use that same constant. The receipt deduplication window remains 24 hours. Retries use the same plan and receipt, never a new attempt because a record expired or was evicted. A correction uses a new plan with the old tracking id and exact revision. Missing records with nonzero expected revisions are refused.
- Keep at most 200 records per room and 100 KiB serialized, for **up to 24 hours** from first Apply. Prune expiry using stored op envelope time, never the replay machine's clock. If a new record would exceed either cap, evict the oldest by first-Apply time, breaking ties by tracking id, until it fits. At 200 records this evicts the oldest, not the new Apply. Eviction has the same consequences as expiry below and commits atomically with the successful outcome. A refused outcome evicts nothing. Never downgrade to untracked Apply. Validate per-record limits alongside the existing 56 KiB outcome bound.
- Each tracked UndoEntry carries its tracking id and plan. The server adds a bounded `saveOutcome` transition to `sys.restore`, naming the exact current revision and the expected plan. Undo requires `applied`, and Redo requires `undone`. It changes status and increases revision in the same transaction as the guarded restore. Carry that identity through `pushRestored`. Never restore lifecycle metadata through a generic entity inverse, where an unrelated restore could unlock the page.
- Write every ledger creation, update, expiry prune and capacity eviction with **Tx bookkeeping writes**. `Tx.inverse()` must contain no ledger key, including when the outcome also changes actors. The explicit lifecycle transition alone changes its applied/undone status on restore.
- A successful tracked outcome always records one Play step, even when `Tx.inverse()` returns null. For example, 2 fire damage becomes 1 after a pass and 0 after resistance: it commits an HP log line but changes no entity. Store an empty entity inverse with the lifecycle identity. `sys.restore.entries` may be empty **only with a validated `saveOutcome` transition**. Schema presence is insufficient: the reducer requires the current record, plan, revision and state to match. Empty ordinary restores remain invalid. Undo/Redo advance status and transfer a lifecycle-only step even when the reducer again returns a null entity inverse. Duplicate Apply receipts create no second step, and these restores leave player projections and notices unchanged.
- Undo/Redo of an expired or evicted record with a nonempty entity inverse can still restore game state under ordinary guards, but cannot reopen a page or recreate its record. The DM notification says the page can no longer reopen. A lifecycle-only step with no retained record refuses and drops, since no step in this DM's other scope caused expiry/eviction. A retained mismatched record refuses the whole restore under section 3.1's rule. A superseded outcome cannot unlock or relock its replacement.
- A tracked outcome is one unmerged step regardless of a supplied gesture group. Replaying an old first-Apply receipt after Undo returns that original receipt, but the newer status revision wins. Clients reconcile by revision and confirmed room sequence, never arrival order, and wait until the view covers the receipt's sequence before deciding that a record is missing.

Batch A's live stack `undo`/`redo` requires `head` and optional `scope: play | setup`, default Play. Missing `head` says "Reload to use Undo" before selection. `undo.of` is Play only and also checks origin. `undo.log` is a separate, mutually exclusive branch without a head. DM-only `discard: true` requires the expected head retained for a state conflict. Players cannot select Setup, discard or declare setup groups. Dispatch gains `groupScope: setup` only with a group id. Store scope and safe correction data on the resolved restore for replay. Private `history` messages carry room-load epoch, confirmed sequence and per-member serial advancing on every stack change, drop/discard included. Send after committed snapshot/events. Keep existing strict envelopes unchanged so old clients parse refusals/acks and ignore unknown history. Only the current connection's history after its snapshot establishes an epoch. Drop frames from older connections/retired epochs, compare serials within the accepted epoch, and hold summaries until the view covers their sequence. Send only that member's heads/labels, never Setup to players. **UNDO-ASTRA-08.** A covering history summary follows every delivered state event, even when the member's stacks and serial are unchanged, such as a chat line. An equal serial with a newer sequence or watermark is allowed, so a view that has caught up to an event is never left waiting for a summary that would otherwise be skipped. Batch B adds lifecycle, page ask/close reasons, request value hashes and embedded recharge use.

Add the optional ledger to snapshot validation, keys/reads/projection plumbing where required, and export validation. Normal server snapshots retain it. Import into a new room deliberately drops it, as it drops open requests, since local drafts and undo stacks do not move rooms. Do not remap stale identities into live pages. Local checkpoint storage is versioned, bounded to one active page plus its latest pre-Apply and optional redo-held draft, with validated fields and a 512 KiB aggregate limit. If it cannot be saved durably, keep it in memory and say "This save can reopen here until this tab closes." A missing in-memory checkpoint cannot unlock either.

Batch A uses op **34**, identity migration **33 to 34**, and snapshot **30**, identity migration **29 to 30**. Its stored correction events extend the closed `logEvent` union. Room loading replays only ops after the snapshot sequence, so op gates alone cannot protect an older reader once a snapshot covers A's ops. Snapshot 30 gives that reader a clean version refusal. Gate notices by original stored op version, preserving older state and log numbering. Old `actor.outcome` payloads stay valid without `page`, and old snapshots gain no invented statuses. A's v30 and B's v31 snapshots are separate rollback boundaries, even with no correction event or ledger record currently present.
