# raccoon-vtt: RaccoonVTT on your own computer

Status: designed, 2026-11-13, building. The design passed five review rounds (Review, near the end, says what they changed). Code is cited from main at df8cfd49 (room format 46, change format 60), and none of the files it changes differs at the build's base, 076c8a09. The feature steps neither format. Decisions are marked [051] for D-261113-051 and so on (section 16), and D-261113-070 and 074 to 077 were settled before the review and are used as written. As built, at the end, lists every place the build went its own way.

The project owner asked on 2026-11-01: "Please design a way for the application to be run on someone's local pc (windows/mac/linux) so that someone can easily run this as a stand alone application rather than having to set it up on a server. This would allow them to run the app while on their computer so players can join on the local network. Don't build this but come back to me with the design/build system for this. Everyone would still use a web browser."

On 2026-11-13 the owner took the answers draft 1 suggested to its five open questions: "all suggestions are good w me" (D-261113-050, section 15). Release order: v0.4.0 without the desktop app, v0.5.0 with it.

## 1. What the DM gets

1. One download from the GitHub Release (11.5). Installing needs no Docker, Postgres, Node or terminal. It runs on Windows 10 or 11 (x64), macOS 15 or later (Apple silicon or Intel), and Linux with glibc 2.36 or later (Ubuntu 24.04, Debian 12, Fedora 37 and up) [074].
2. Opening it shows a small window and opens the DM's default browser at `http://localhost:3170` (3170, or the next free port on first run, then kept).
3. The window shows the address players type, its QR code, and the switch **Players on this network can join**, on by default. Players on the same network open that address in their own browser and play as on a hosted server.
4. On Windows and macOS, closing the window keeps RaccoonVTT running in the notification area or menu bar. On Linux, closing minimizes the window, because GNOME shows no tray icon without an extension and a hidden window would leave no way to quit [063]. **Quit** stops everything cleanly. Opening the app again while it runs brings the window back and opens the browser.
5. Rooms, images and backups stay on the DM's computer. Room export and import move a room between a local install and a hosted server, as today.

Out of scope: play over the internet (port forwarding or a tunnel makes a home computer a public server, and a hosted install is the answer), the DM's own view inside the shell, mobile hosting, Windows on Arm builds (x64 runs under emulation, untested), rpm and Flatpak, start at sign-in, an admin page.

## 2. Shape

Four kinds of process, all on the DM's computer:

- **Shell** (Electron, `desktop/electron/` for the code that imports Electron, `desktop/shell/` for its logic): tray, window, single-instance lock, updater, power save blocker. It starts the supervisor and passes the window's requests to it.
- **Supervisor** (`desktop/runtime/`, run as `raccoonvtt-server desktop/runtime/main.ts`, the bundled Node renamed so Task Manager and firewall prompts name the app): data folder, secrets, settings, PostgreSQL, the app server, backups, restore, network detection, version checks. It talks to the shell over Node's IPC channel on stdio, never a port. The shell spawns it with `detached: true` and the IPC channel kept [088], so on Windows it is outside the shell's job object and outlives the shell long enough to act on the channel closing: it stops the app server and PostgreSQL cleanly and exits.
- **App server**: today's `server/main.ts`, run by the supervisor with the same Node and an env built from scratch: no inherited `NODE_OPTIONS`, proxies or `PUBLIC_ORIGIN`, while `SystemRoot`, `TEMP` and `TMP` are kept on Windows. It is the only process players reach.
- **PostgreSQL 17**: started and stopped with `pg_ctl` by the supervisor, on 127.0.0.1 only, on a free loopback port picked at each start (bind 127.0.0.1:0, release, pass with `-o "-p <port>"`, three tries), so a PostgreSQL already on 5432 never matters. `DATABASE_URL` is built at each start [084].

Every child process is spawned with `windowsHide: true`, and none runs through a shell. `--headless --data <dir> [--port <n>] [--network on|off]` runs the supervisor without Electron, printing one status line per change and stopping cleanly on Ctrl+C. The smoke tests use it. It is not documented for DMs in v1.

## 3. Choices, with the options rejected

**Shell: Electron**, built with electron-builder: tray, window, single instance and power save blocking alike on all three systems, JavaScript like the rest, and installers plus a GitHub Releases updater.
- Rejected, Tauri: adds Rust, depends on the system WebKitGTK version on Linux, and still needs the Node sidecar.
- Rejected, no shell (Node plus the browser): no tray, nothing visible on macOS, a console window on Windows. The owner accepted the larger download (question 3).

**Runtime: bundled official Node 24.21.0** (ci.yml's `NODE_VERSION`) [051], pinned per target by URL and SHA-256 from nodejs.org's SHASUMS256.txt. The server's `.ts` files run as in the image, and sharp and @node-rs/argon2 load their Node-API prebuilds.
- Rejected, Electron's `utilityProcess`: type stripping there is not guaranteed.
- Rejected, `ELECTRON_RUN_AS_NODE`: needs the RunAsNode fuse on (6.6).
- Rejected, compiling the server to JavaScript for the desktop: a second build the tests never run.

**Database: PostgreSQL 17 from theseus-rs/postgresql-binaries** [067], release 17.11.1 (2026-10-18, the newest 17.x at least two weeks old, moving to 17.12.x after 2026-11-26), pinned per target by SHA-256 in `desktop/pins.json`, and checked with `gh attestation verify --repo theseus-rs/postgresql-binaries` (GitHub holds attestations for the digests). Each target's `.manifest.json` lists postgres, initdb, pg_ctl, pg_dump and pg_restore. `desktop/scripts/fetch-runtime.ts` prunes by a deny list (every program in `bin/` but those five, `libLLVM*`, `llvmjit*`, `lib/bitcode/`, Python and `lib/python*`, `plpython*`, `pltcl*`, `plperl*`, `include/`, `*.a`, `pgxs`), leaving about 70 MB unpacked, 22 MB packed. `jit = off`, since llvmjit is gone. Then it checks what is left:
- **Windows** [075]: the archive imports the VC++ runtime and holds none of it, so `MSVCP140.dll`, `VCRUNTIME140.dll` and `VCRUNTIME140_1.dll` (x64) go in `postgres/bin` beside the programs [098]. Microsoft publishes no download of the loose DLLs, so they come from the Windows runner's Visual Studio folder `VC\Redist\MSVC\<version>\x64\Microsoft.VC143.CRT`. A hash pin would break at every runner image update, so instead each must carry a valid Authenticode signature from Microsoft Corporation, and the fetch step checks that they are new enough three ways [103]: every function any retained PE file (programs and bundled DLLs alike) imports from `MSVCP140.dll`, `VCRUNTIME140.dll` or `VCRUNTIME140_1.dll` is exported by the shipped copy, each DLL's four-part file version is at least the floor `vcRuntimeMin` pinned in pins.json beside each PostgreSQL pin (set when the pin is chosen, to the version that passed the Windows smoke test), and, as an extra check only, at least the highest PE linker version among the retained files (major and minor, which is all a PE header holds). The build logs the version it shipped. The script lists the imports of every PE file left and fails on any DLL that is neither in the tree nor on a short system list (`KERNEL32`, `ADVAPI32`, `USER32`, `WS2_32`, `SECUR32`, `SHELL32`, `OLE32`, `CRYPT32`, `BCRYPT`, `api-ms-win-*`, `ucrtbase`).
- **Floors** [074]: the highest Mach-O `minos` of the binaries left (today 15.0) and the highest `GLIBC_` version any of them needs (today 2.36, through the bundled libstdc++ that ICU loads) must not exceed the floors in pins.json (`macos: 15.0`, `glibc: 2.36`). A newer pin that raises them fails the build until the floors and the docs change together.
- Rejected, zonky's binaries (no pg_dump or pg_restore), building PostgreSQL ourselves (the MSVC and relocation work theseus-rs already does, and older floors are not worth it, D-074), running Microsoft's 25 MB redistributable from the installer (D-075), PGlite (one connection), SQLite (a rewrite), requiring Docker.

**Window: a page the shell serves** at `app://raccoonvtt/` from its own Vite build (`desktop/window/`), React with `client/lib/theme.ts` and the app's components [053]. It works while the app server is down, when the DM needs it most.

**Plain HTTP on the network.** Players open `http://192.168.x.y:3170`. Chrome's "Always Use Secure Connections", on by default since Chrome 154, exempts private addresses: the page shows "Not secure" and no warning page, unless the player chose the stricter setting, which shows one they can click through. The DM, on `localhost`, keeps a secure context.
- Rejected, self-signed HTTPS (a warning on every device, hard to accept on phones) and a local certificate authority (a root certificate on every player's phone).

**Addresses, not names** [064]. Rejected, an mDNS name: Android resolves `.local` unreliably, and on macOS 15 advertising one triggers the Local Network prompt.

## 4. Server changes (local mode)

Local mode is `NODE_ENV=production` plus `RACCOON_MODE=local` [054]. `production` keeps meaning a built app. `config.local` turns off what assumes one HTTPS origin behind a proxy. Only the supervisor and the e2e harness set it.

## 5. Client changes (plain HTTP)

- **Share links** [086]: `client/lib/shareOrigin.ts` exports `useShareOrigin()`, which returns `config.local?.shareOrigin ?? location.origin` and reads `/api/config` lazily: when a share surface mounts, at most once per 5 s while one is shown, when the window regains focus, and when the room's connection state returns to `open` after a reconnect (the switch, a port change and a restore all restart the server with 1012). So turning the switch on, Windows moving the network to Private and a new address all reach the open DM tab without a reload. Every link built for someone else uses it: Home.tsx (DM link), MenuPanel.tsx (join link), Access.tsx (player and DM links), TableDisplay.tsx (display code), PlayerLinkShare.tsx (player link and QR code). `LoadBoundary.tsx`'s `location.origin` is not a share and stays.
- **Copying**: `navigator.clipboard` is undefined on an insecure origin, so the `writeText` calls in Home.tsx, MenuPanel.tsx and controls.tsx throw today. `client/lib/clipboard.ts` `copyText(text)` tries `navigator.clipboard.writeText`, then a selected off-screen textarea with `document.execCommand("copy")`, and when both fail selects the visible text and says "Selected. Use your device's Copy." Choices.tsx's seed copy uses it too.
- **Already safe without a secure context** (checked at main): Share hides without `navigator.share`, the wake lock is skipped (a table display on the LAN cannot keep its screen on, so the guide says to turn the TV's sleep off), `navigator.locks` and `navigator.keyboard` are checked before use, `crypto.randomUUID` has a fallback, image paste uses the paste event, and the WebSocket scheme follows the page's.
- **The audit as a test**: `client/lib/secureContext.test.ts` scans client/ and shared/ for `navigator.clipboard`, `navigator.share`, `navigator.wakeLock`, `navigator.locks`, `navigator.keyboard`, `crypto.randomUUID`, `crypto.subtle`, `serviceWorker`, `audioWorklet` and `showSaveFilePicker`, and fails on any use outside a listed, guarded file.
- **Home on another device** (`createHere` false) [081]: CreateCard and ImportRoomCard are both replaced by "New rooms are made on the computer running RaccoonVTT. Join with the room's link, or its ID and password." When `hostPage` is set, it reads instead "This is the computer running RaccoonVTT. Make rooms on its own page." with **Open it** linking `hostPage`. The join card stays.

## 6. Security on a LAN over plain HTTP

**Who can reach what**
- The app server listens on 127.0.0.1 with the switch off, and on 0.0.0.0 (IPv4 only) with it on. PostgreSQL listens on 127.0.0.1 only, on a port picked at each start, with no Unix socket, scram-sha-256, a random 32-byte password, and a `pg_hba.conf` admitting only user `raccoon` from 127.0.0.1/32 [084].
- With the switch on, a connection from any address outside 127/8, 10/8, 172.16/12 and 192.168/16 is closed before HTTP: a forwarded port, a public IPv4, CGNAT and Tailscale (100.64/10) and link-local addresses are refused. A private address proves a device is on some private network, not that it is on this Wi-Fi: a routed private network, a VPN or a proxy can present one. The design assumes the network the computer is on is one the DM trusts.
- Every request must name an allowed Host, so a domain an attacker re-points at this computer (DNS rebinding) gets 421.
- Every unsafe request and WebSocket upgrade must come from an allowed Origin (6.2).
- Room creation and room import accept only requests whose socket address is loopback [081], checked before the body, so a guest on the Wi-Fi can neither fill the disk nor tie up the CPU with an import.
- There are no host-only HTTP routes [053]. The window's controls travel over Electron IPC to the supervisor, which nothing on the network can reach.

**Cookies and CSRF.** Session cookies are HttpOnly, SameSite=Strict and Path=/ without Secure, which plain HTTP needs. A cookie belongs to a host name, not a port, so any other service on this computer (at `localhost` or the LAN address, on any port) receives the RaccoonVTT cookies its visitors' browsers hold, and a page it serves counts as same-site. CSRF still holds, because a request from that page carries its own Origin, which the allowlist refuses. CSRF has two locks, as on a server: SameSite=Strict, then Sec-Fetch-Site or the Origin allowlist. JSON bodies only, and `text/plain` is still refused.

**The players' join path.** A player opens the share link (`/r/<id>#pw=<password>`, the password in the fragment, never in a request line or log), the join page posts the password, and the server sets the session cookie. Asking to join works as on a server (8 waiting per address, 50 per room). Local mode has no Turnstile keys, so the join route skips its per-room challenge, password guessing is limited per address only, and a device on a LAN can take many addresses. A room's safety then rests on its password, which is why the form suggests a three-word passphrase. A player whose address changed joins again and picks themselves from the player list.

**A public or work network** [062][077][088][094]. Windows marks each network Public, Private or Domain. One long-lived hidden PowerShell child, run by its absolute path (`%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -EncodedCommand ...`, since Windows looks in the current folder before PATH), reads `Get-NetConnectionProfile` with `Get-NetIPAddress` every 5 s and prints a full sample each time, changed or not, with a sequence number. A sample is fresh for 15 s. With no fresh sample (the child hung, exited or printed something unreadable) the watcher has failed: the server binds 127.0.0.1, and the child is killed and started again after 1, 2 and 4 s, then every 30 s. The supervisor starts closed: it waits up to 10 s for the first sample before choosing HOST, so a normal start binds once, and binds 127.0.0.1 until a fresh sample says Private. On a Public or Domain network, on a network with no profile, or with no fresh sample, the server binds 127.0.0.1 whatever the switch says, and the window explains (section 9). A change to Public is acted on within 5 s, and a stalled watcher within 15 s. macOS and Linux have no such label, so there the switch alone decides.

**The firewall rule.** The Windows installer is per-machine (one UAC prompt). It runs `netsh advfirewall firewall delete rule name="RaccoonVTT"`, then `netsh advfirewall firewall add rule name="RaccoonVTT" dir=in action=allow program="$INSTDIR\resources\node\raccoonvtt-server.exe" protocol=TCP profile=private enable=yes`, so a reinstall or update leaves one rule. The uninstaller deletes it. Windows does not prompt when a rule for the program exists, and blocks it on public and domain networks. The macOS application firewall is off by default. When on, it asks once per build about `raccoonvtt-server`, since an ad-hoc signature changes with each build. Linux desktops usually run no firewall, and the window's "Not working?" fold gives the `ufw` command.

**A person on the same network who is not a player** can open the address and see the Home and join pages, the starter art and `/healthz`. Without a room's ID they see nothing of any room. With the ID they see its name and can ask to join, which the DM can turn away, or guess its password, limited per address. They cannot create or import rooms, reach the database, or use the window's controls. Someone who can watch or change the network's traffic (an open network, a WPA2 network whose passphrase they have, a device they control on it) can do much more, because the address uses plain HTTP: read passwords and session cookies as they pass, change the pages a device loads, and use a session as their own. Sessions are bearer tokens, so a captured DM cookie or DM link is full DM control of that room, deleting it included. That covers a DM link opened on a tablet over the LAN. The DM's own browser on this computer talks over `localhost`, which never leaves the computer.

**6.1 What the design guarantees, in plain words** (the docs carry this text). "Only devices with a private network address can open RaccoonVTT, and only while Players on this network can join is on. Rooms can be made only on this computer. The database, backups and settings are reachable only from this computer. Nobody can see a room without its link or password or the DM letting them in, and a room's password is guarded only by a limit on guesses from each address, so pick a long one. The connection isn't encrypted: someone on your network who can watch or change its traffic can read a password, change what a device shows, or take over a player's or DM's session. Use it on a network you trust, open your DM link only on this computer when you can, and turn the switch off on any other network."

**6.2 Allowed origins, exactly.** `http://localhost:P`, `http://127.0.0.1:P`, and `http://A:P` for every private IPv4 address A of this computer while the switch is on. Hosts are the same without the scheme. P is the configured port. `Origin: null` is never allowed. Local pages send `referrer-policy: same-origin` [080].

**6.3 Updates.** The updater fetches `latest*.yml` and installers over HTTPS from the GitHub Release and checks each installer's SHA-512 from it, refusing downgrades and prereleases. Sigstore bundles exist for every asset, but the updater does not check them in v1, so a compromised GitHub account could ship an update, as it could ship an image.

**6.4 The window.** `contextIsolation`, `sandbox`, no `nodeIntegration`. It loads only `app://raccoonvtt/`, with `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'none'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'`. `will-navigate` is prevented and `setWindowOpenHandler` denies, opening only `http://localhost:P/...` and the release page in the default browser. The preload exposes `window.raccoonLocal` (desktop/contract.ts), and the shell checks every argument with zod.

**6.5 Secrets and logs.** `<data>/secrets.json` holds `ROOM_SECRET_KEY` and the database password. The data folder is mode 0700 and secrets.json 0600 on macOS and Linux, and Windows keeps the per-user `%LOCALAPPDATA%` ACL. Neither secret reaches a log, the window or a backup.

**6.6 Electron fuses** (@electron/fuses in `desktop/build/afterPack.mjs`): RunAsNode, NODE_OPTIONS, `--inspect` arguments and file protocol privileges off. Cookie encryption, embedded asar integrity (macOS and Windows) and only-load-from-asar on.

## 7. Networking

- **The switch** writes `networkPlay` to settings.json and restarts the app server with the new HOST, closing sockets with 1012 so phones reconnect within seconds (about 3 s, shown as busy).
- **Port**: 3170, or the first free one above it on first run, saved. Free means nothing listens on 0.0.0.0, 127.0.0.1 or `::1` there, since `localhost` may resolve to `::1` first. Taken at a later start: the window offers the next free port and says links will change. Changing it in Settings restarts the server.
- **Sleep**: while any socket is open, the DM's own tabs included, the shell holds `powerSaveBlocker` "prevent-app-suspension", released 60 s after the count reaches 0. Closing a laptop's lid still sleeps it.
- **Address changes** show in the window within 5 s. The new address joins the allowlist at once, and open DM tabs pick it up (section 5).
- **Clock** (log lines are numbered by the server's clock). All three systems set the time automatically by default. During the daily update check the shell compares the response's `Date` header with the clock and warns past 2 minutes. An export from a computer whose clock ran ahead is refused by a server more than 5 minutes behind it, as between any two servers.

## 8. Data, backups, updates

**8.1 Where data lives** [059][076]. `--data <dir>` or `RACCOON_DATA_DIR` overrides it.
- Windows: `%LOCALAPPDATA%\RaccoonVTT\data`. Not Roaming, which a roaming profile copies at sign-in and sign-out.
- macOS: `~/Library/Application Support/RaccoonVTT/data`.
- Linux: `${XDG_DATA_HOME:-~/.local/share}/RaccoonVTT`, shared by the AppImage and the deb.

It holds `postgres/` (initdb with `--encoding=UTF8 --locale=C --locale-provider=builtin --builtin-locale=C.UTF-8`, so neither text order nor messages depend on the environment's locale or ICU), `assets/`, `backups/`, `logs/` (server, supervisor, shell and postgres logs, each rotated at 10 MB, 5 kept), `secrets.json`, `settings.json` (port, networkPlay, checkUpdates, openBrowser, animatedMaps, roomSound, zod-checked, an invalid file replaced by defaults and kept as `settings.json.bad`), `restore.json` while a restore runs (8.3), and on Windows, when the folder's path is not plain ASCII, `postgres-link.json` (As built). The format stamp lives in the database, not in a file (8.4). One supervisor per data folder [084][092]:
- **Identity**: the SHA-256 of the folder's canonical path, from `fs.realpathSync.native` (symlinks, junctions and short names resolved), case-folded on macOS and Windows, whose usual file systems ignore case. `<hash>` is its first 16 hex.
- **Lock**: on Windows a named pipe, `\\.\pipe\raccoonvtt-<hash>`, which Windows removes when its owner ends. Elsewhere a Unix socket `raccoonvtt-<hash>.sock` in a per-user folder that no caller's environment can move: on Linux `/run/user/<uid>` (the folder `$XDG_RUNTIME_DIR` names, checked to be the user's own with mode 0700), on macOS the per-user temp folder from `getconf DARWIN_USER_TEMP_DIR` (the `TMPDIR` a GUI app gets, read without trusting `$TMPDIR`). Where neither exists (Linux without logind), or where the socket's path would pass the limit (107 bytes on Linux, 103 on macOS) [105], `~/.cache/RaccoonVTT/`, created with mode 0700 and checked to be the user's own. If even that path is too long, the start stops with "RaccoonVTT can't start because your home folder's path is too long for it." Never the shared `/tmp`.
- **Taking it**: listen. If the name is in use, connect. A connect that answers means another owner: "already running". A refused connect means a stale socket, replaced only under the recovery guard [101]:
  - The guard is a folder, `<socket>.recover`, made whole in one step: its owner record (pid, the start time the OS reports, the boot time) is written into a uniquely named folder beside it, which is then renamed to `<socket>.recover`. A rename onto a folder that exists and is not empty fails, so only one contender gets the guard, and a guard never exists without its record.
  - Holding the guard: connect once more, and only if that is still refused, unlink the socket and listen. If that connect answers, remove the guard and stop as "already running".
  - Finding the guard taken: read its record. If that pid is alive with that start time in this boot, its owner is working, so wait 100 to 300 ms (random) and start over, giving up as "already running" after 5 s. Age alone never frees a guard, so a recovering owner that is merely slow keeps it.
  - No one but its owner ever renames or removes a guard [106]. A rename or an unlink acts on whatever is at the path at that moment, so a contender acting on a record it read earlier could remove a newer owner's guard. A guard whose owner is gone was left by a supervisor that died in the few milliseconds it holds one. That start, and every later one until the folder is gone, stops with "RaccoonVTT closed while it was starting last time. If no other copy is open, delete the folder <path> and open RaccoonVTT again." The window shows the full path with a Copy button, on Linux adds "or restart the computer" (`/run/user` is cleared at boot), and offers Delete it and start behind a confirmation that no other copy is open. A record that cannot be read (a damaged file) stops the start the same way, with "RaccoonVTT can't tell whether another copy is running. If no other copy is open, delete the folder <path> and open RaccoonVTT again."
  - After listening, the new owner connects to its own socket and checks the nonce that answers, then writes the owner record below before it removes the guard.
- **Owner record**: with the lock held, `<data>/supervisor.json` (a durable write, 8.3) holds the pid, the start time the OS reports for it, and the lock's path. A starting supervisor that got a lock but finds a record whose pid is alive with that start time also stops as "already running". That covers two locks that still differ (a canonical path that changed between two starts). A reused pid has another start time, so it never counts.
- Tests (`desktop/runtime/lock.itest.ts`, real processes): ten supervisors at once on one folder leave one owner. A guard holder paused for 30 s between its last connect and its unlink keeps the guard, and no second owner appears. A guard whose owner died stops every contender with its words and is never removed by one, including ten contenders at once and one paused for 30 s after reading the record while another reads it too. Once the folder is deleted, the next start takes the lock. A damaged guard record stops the start with its words. A path over the limit falls back to `~/.cache/RaccoonVTT/`. Paths that alias one folder (a symlink, other case on macOS and Windows) and different `TMPDIR` and `XDG_RUNTIME_DIR` values leave one owner. Two contenders recovering one stale socket leave one owner. The first owner's database keeps answering queries throughout.

**8.2 Backups** [060][083]. `desktop/runtime/backup.ts` keeps backup.sh's model in Node, so it runs on Windows: a run is good only once its completion record exists, images go to one shared, content-addressed store, and a failed run deletes nothing.
- Consistent by construction: a REPEATABLE READ transaction runs `select pg_export_snapshot()`, `pg_dump --format=custom --exclude-table=backup_runs --snapshot=<id>` dumps it, and the asset rows are listed in the same transaction and mapped to files with server/assets/store.ts's path helpers.
- Read the dump back whole (`pg_restore --list` and `pg_restore --file=<null device>`). Copy each listed image the store lacks, from `assets/` or, when it was deleted after the snapshot, from `assets/trash/<day>/`, as backup.sh's lookup does (docker/backup.sh:181-200). An image already in the store at the same length is kept. Write `<name>.files`, then `<name>.good.json` last.
- The record: started, finished, kind (`daily`, `manual`, `before-update`), `dataApp`, `snapshotVersion` and `opVersion` of the data, the PostgreSQL major, `forVersion` (before-update only, the version being installed, for the label), dump bytes, `dbBytes` (the database's size, for the restore's space check), image count. The app version and formats are read from the database's stamp row (8.4) in the same snapshot as the dump, so they are the data's own: the old build's for a before-update backup. The dump carries the row too.
- When: **Back up now**, before an update (8.4), and in the background once the server is up and then every 24 h while it runs, whenever the newest good backup is over 24 h old.
- Keep the newest 7 daily or manual, the newest of each of the last 4 weeks, and the newest 3 before-update. Prune store files no kept backup lists. Always leave 2 GiB free, ending as partial when it cannot.
- No secrets and no settings in a backup. The room secret key stays in secrets.json, so a restore on the same computer shows DMs their player links.

**8.3 Restore** [082][090][091][100][102][104] (window only). The original database is never dropped or changed until the restored one is complete, its images are on disk, and it is in its place. Every next-start action is chosen from what the databases are. A crash or a lost journal write at any point therefore ends with either the old data or the restored data, whole.

**Names and tags.** `raccoon` is the live database. The restore builds into `raccoon_restoring` and keeps the original as `raccoon_before_restore` until the end. Each restore has an id, and the database it builds carries it as its comment (`COMMENT ON DATABASE`): `raccoonvtt-restoring:<id>` while pg_restore runs, `raccoonvtt-restored:<id>` once it is complete and checked, and `raccoonvtt-finished:<id>` once step 6 has dropped the original [107]. The app uses neither name nor comment for anything else. The tag stays on `raccoon` after the restore, harmless, so `raccoon` tagged with the journal's id is known to be this restore's data, and anything else is the original. `raccoon` and `raccoon_before_restore` exist together only between step 5's second rename and step 6's drop, when `raccoon` is the restored copy. A `drop database` only ever names `raccoon_restoring`, `raccoon` while `raccoon_before_restore` exists beside it and it carries a `restored` tag, or `raccoon_before_restore` while `raccoon` carries the journal's id.

**What must be durable, and where.** Each database carries its own format stamp (8.4), so the stamp moves with the data through every rename and drop, as durable as PostgreSQL makes any commit, on every system. The only file the restore depends on is the journal `<data>/restore.json` (id, backup name, state). It is written with `desktop/runtime/durable.ts`: a temp file in the same folder, fsync, rename over the target, then an fsync of the folder. Node's fsync issues `F_FULLFSYNC` on macOS (libuv). On Windows, Node can neither fsync a folder nor pass `MOVEFILE_WRITE_THROUGH`, so the renamed file is opened again and fsynced (`FlushFileBuffers`), as PostgreSQL itself does on Windows for its own files. That flush is best effort for the rename, and nothing depends on it: a journal write that is lost, or a deleted journal that comes back, leaves a database state that a row of the table below handles, and every row ends with old or restored data whole. The table never takes the journal's word over the databases'. It only uses the journal to pick between finishing and undoing when both are safe, and for the backup's name and date. `supervisor.json` is written the same way.

**Steps**
1. Refuse a backup whose recorded formats are newer than this build's, one missing any listed image from the store, and any restore when free space is under the backup's `dbBytes` plus 2 GiB ("Not enough free disk space to restore safely").
2. Stop the app server and wait for its `stopped` report. It stays stopped until step 7, so nothing can move an image to trash in between, as server/assets/store.ts `deleteIfUnreferenced` does the moment a file loses its last row. While the restore runs, the window refuses Rooms on this computer and Back up now ("Not during a restore"), and no daily backup starts [104].
3. Journal `preparing`. Check every listed image at its path in `assets/` by length, and copy each missing or short one from the store (through `.restoring` files checked by length, never overwriting a whole file). Then fsync every listed image, copied or found, and every folder that holds one. For every folder the copy created, also fsync the folder that holds it, up to the first one that already existed: `assets/` when a new two-character shard folder was made (server/assets/store.ts `variantPath`) [108]. All of this happens before anything else [100]. On Windows each file is opened and flushed, which makes its data durable, and its name is as durable as the flush makes it (best effort, as above).
4. Drop `raccoon_restoring` if it exists (only ever this app's leftover). Create it with the `restoring` tag, run `pg_restore --no-owner --single-transaction --exit-on-error` into it, check that it reads (`select count(*) from rooms`), set its stamp row's app version to this build (keeping the backup's formats, and inserting the row from the backup's record if the dump has none), so the next start takes no before-update backup [096], and set the `restored` tag.
5. Journal `swapping`. Close the supervisor's own pool connections to `raccoon`, and from a connection to the `postgres` database end any other session on `raccoon` or `raccoon_restoring` (`pg_terminate_backend`). Then `ALTER DATABASE raccoon RENAME TO raccoon_before_restore`, and `ALTER DATABASE raccoon_restoring RENAME TO raccoon` [104].
6. Journal `finishing`. Drop `raccoon_before_restore`, set `raccoon`'s tag to `raccoonvtt-finished:<id>` [107], then delete the journal.
7. Start the app server: "Restored the backup from <date>."

A failure in step 3 or 4 drops `raccoon_restoring`, deletes the journal, and starts the server: "The restore failed, and nothing changed." `raccoon` is never touched there. A failure in step 5, or in step 6 before the drop, runs the undo and says the same. A failure after the drop is left for the next start (the table's row for it).

**At the next start**, after `pg_ctl start` and before the version checks, the supervisor reads the databases (R `raccoon` and its tag, B `raccoon_before_restore`, N `raccoon_restoring` and its tag) and the journal, and does the one row that matches. "Own" means R's tag carries the journal's id. **Undo**: journal `undoing`, drop R only if B exists and R carries a `restored` tag, rename B to `raccoon` if there is no R, drop N, delete the journal. **Finish**: check every image the journal's backup lists, copying and flushing any missing one from the store as in step 3, then step 6. When the backup or its file list is gone (deleted by hand), finish logs it and skips the check: every row that finishes is reached only after step 3 flushed every listed image. Each part of either does nothing when its database or file is already gone, so either one cut off anywhere is completed by running it again.

| Databases at start | Journal | Crash point that leaves it | Next start does | Window says |
| --- | --- | --- | --- | --- |
| R, no B, no N | none | no restore, a finished one, or before step 3's journal write | nothing | nothing |
| R not own, no B, no N | any state | in step 3, in step 4 before N was created, or at the end of an undo | delete the journal | "A restore was interrupted, and nothing changed." |
| R own and tagged `finished`, no B, no N | any state | after step 6 set the tag: the journal's delete lost, or a deleted journal that came back | delete the journal (no backup needed) [107] | "The restore of the backup from <date> finished." (harmless when the journal came back long after) |
| R own and tagged `restored`, no B, no N | any state | in step 6 after the drop, before the `finished` tag | check the images as in finish, set the `finished` tag, then delete the journal | "The restore of the backup from <date> finished." |
| R, N with any tag, no B | any or none | in step 4, in step 5 before its first rename, or in an undo after B was renamed back | drop N, then the matching row above | by that row |
| no R, B, N tagged `restored` | `undoing` | in an undo of a failed second rename | rename B to `raccoon`, drop N, then the matching row above | "A restore was interrupted, and nothing changed." |
| no R, B, N tagged `restored` | anything but `undoing`, or none | in step 5, between its two renames | rename N to `raccoon`, then the matching row below | by that row |
| R own, B, no N | `swapping` or `finishing` | after step 5, or in step 6 before the drop | finish | "The restore of the backup from <date> finished." |
| R tagged `restored`, B, no N | none, `preparing`, `undoing`, or R not own | step 5 or 6 with a journal write lost, or in an undo before R was dropped | undo | "A restore was interrupted, and nothing changed." |
| no R, B, no N | any or none | in an undo after R was dropped | rename B to `raccoon`, delete the journal | same |
| no R, B, N tagged `restoring` | any | cannot happen, since step 5 runs only after the `restored` tag | rename B to `raccoon`, drop N | "A restore was interrupted, and nothing changed." |
| anything else (R without a `restored` tag beside B, R, B and N together, N with no R and no B, no databases with a journal) | any | cannot happen by these steps | nothing destructive: stop with an error | "A restore left the databases in a state RaccoonVTT can't sort out by itself. Nothing was deleted." |

Images: every row that keeps the restored data either runs after step 3 flushed every listed image (rows reached after step 5), or checks them again from the store before it deletes the journal (finish). The `finished` tag is set only after that, so a journal that comes back after retention pruned its backup is deleted without the backup [107]. A power loss in step 3 or 4 can lose at most copies that the restore had not yet relied on, and the rows for those points undo. The one gap left is Windows, where a copied image's name is only as durable as NTFS makes a flushed rename, and a power loss right after step 6 deleted the journal could leave that image missing. A second restore of the same backup puts it back.

Tests (restore.itest.ts): each row, reached by killing the supervisor at its crash point (`RESTORE_TEST_CRASH_AT`, read only in tests, as backup.sh's `BACKUP_TEST_*`), and again with the journal write before that point dropped, each ending with the old or the restored data whole and the images every room names present. Order checks on a recorded file-call log: no rename of a database before every listed image and its folder were fsynced, and no drop before the swap. A failed pg_restore, a failed image copy, an image deleted from `assets/` after step 3 with the journal still present (finish copies it back), a session held open on `raccoon` (ended before the renames), Back up now during a restore (refused), a backup image already present before the restore, an image restored into a shard folder that did not exist (the log shows `assets/` fsynced after the folder was made and before the renames), and a finished restore whose backup retention then pruned, with its old journal put back (the start deletes the journal without the backup) are cases of their own. The randomized test (section 10) runs sequences of crash points, including crashes during an undo.

**8.4 Updates, the pre-update backup and going back** [061][083][088]
- **The stamp** [102]: a one-row table the supervisor owns in the `raccoon` database, `local_app_stamp (app, snapshot_version, op_version, pg_major, written_at)`, created with `create table if not exists` (db/schema.sql never names it, and a hosted server never has it). It holds the app version and the `SNAPSHOT_VERSION` and `OP_VERSION` (shared/migrate.ts) of the build that last ran a server over this data. Kept in the database, it commits as durably as the data, it is in every backup's dump, and a restore brings back the restored data's own stamp. No file holds it. A database with no stamp row counts as this build's only when it has no `rooms` table (a new database: the supervisor reads the stamp before the server's first `applySchema`, server/main.ts) or an empty one. The schema is never applied before these checks. A database with rooms and no stamp row stops the start with "RaccoonVTT can't tell which version wrote this data." and offers Restore a backup, so an older build never reads a newer build's data as its own if a later build moves the stamp. Columns are only ever added to the stamp table, never renamed or removed [109].
- **Before update**: when the stamp's app version differs from this build's, the supervisor starts PostgreSQL alone and takes a `before-update` backup carrying the old data's formats. Only then does it write the stamp with this build's values, before the new server's first start, so a crash during that start still counts as the new build. After the checks, every server start writes the stamp with this build's values in its own committed transaction before the server starts, since a running server may move rooms to its formats as they load. If the backup fails, nothing starts, and the window offers Try again or Start without a backup, the second behind a confirmation. A start right after a restore takes no before-update backup, since the restore wrote this build's version into the restored stamp (8.3 step 4).
- **Downgrade refused cleanly**: when the stamp's `snapshot_version` or `op_version` is above this build's, nothing starts, and the window names the version that wrote the data, with Download the latest version and Restore a backup (listing only backups whose recorded formats this build reads, the before-update one among them). Restoring it brings back its own stamp, so this build then starts, and every change made since that update is lost, as the restore's confirmation says. When no backup this build reads is left (the DM started without one, or retention dropped it), the window offers only the download: "No backup this version can read is on this computer. Install 0.6.0 or later to open your rooms." Any format step blocks a downgrade, which is stricter than the self-hosting "Going back" rules, where a change-format-only step allows going back after a clean stop. One rule keeps the check simple, at the cost of refusing some downgrades a server would allow. An older build with the same formats starts normally.
- **Install** (Windows and the AppImage): electron-updater downloads after **Install and restart**. The shell asks the supervisor to stop, waits for its `stopped` report (the server closed, PostgreSQL shut down cleanly), and only then calls `quitAndInstall`. The NSIS installer itself, whether run by the updater or by hand over a running copy, first runs `"$INSTDIR\RaccoonVTT.exe" --quit` (the running instance gets it through the single-instance lock and quits cleanly) and waits up to 60 s for every process whose path is under `$INSTDIR` to end. It then ends any left (`raccoonvtt-server.exe`, `postgres.exe`, `pg_ctl.exe` under `$INSTDIR` only) before copying files. PostgreSQL recovers from its log after a forced end. A `--quit` run that gets the single-instance lock itself, because nothing of this user's runs (an installer elevated as another administrator), exits at once and starts nothing, and the wait and the ending of leftovers then do the work. The uninstaller runs the same quit, wait and end steps before it removes files [099].
- **Update checks** [069], at start and once a day, on by default with a switch, sending GitHub only the request and a `RaccoonVTT/X.Y.Z` user agent. Windows and the AppImage use electron-updater's `latest.yml` and `latest-linux*.yml`. macOS and the deb read GitHub's `releases/latest` API and offer **Download** (the release page) when its tag is newer and it holds this platform's asset (`-macos-<arch>.dmg`, `_<arch>.deb`). macOS, unsigned, cannot install itself, and apt owns the deb. A release with no desktop assets yet, a missing feed file and a 404 all read as no update, logged at info. Only a network or parse failure logs as an error, and none shows in the window.
- **PostgreSQL major upgrades, later**: every build ships one major. A data folder whose `postgres/PG_VERSION` differs from the bundled major is refused with words naming both. The release that moves to 18 also ships 17's server binaries in `postgres-previous/`, starts the old cluster with them, dumps it with the new pg_dump, creates a new cluster, restores, and keeps the old one as `postgres-17-old/` until the DM deletes it from the window. That release designs and tests its own step.

**8.5 Uninstall and moving.** Every uninstaller (NSIS, dragging the app to the Trash, `apt remove`, deleting the AppImage) leaves the data folder, and NSIS removes the firewall rule. **Show data folder** is the way to delete or copy it. Moving to another computer or a server uses room export and import. The data folder is not portable across systems or PostgreSQL majors.

**8.6 Rooms on this computer** [068]. Whoever runs the computer is its operator, and a DM who clears their browser would otherwise lose DM access to their own room. The window lists rooms with **New DM link** (behind a confirmation). The supervisor runs `scripts/admin.ts --no-schema --json list-rooms` and `--no-schema --json dm-link <id>` as children, with `PUBLIC_ORIGIN=http://localhost:P` so the link is whole, and opens the link in the browser. Two new flags, independent of each other: `--no-schema` skips `applySchema` (its `alter table` lines each take an AccessExclusive lock, which must not happen during play, and the running server has already applied it), and `--json` prints one JSON object. The script works while the server runs, as the hosted docs use it.

## 10. Supervisor states

`stopped, recovering (an interrupted restore, a PostgreSQL left running), starting (initdb when needed, pg_ctl start, version checks, before-update backup, server start), running, restarting (switch, port, profile), restoring, stopping, error`. Order at start: take the lock (8.1), read the old owner record and stop as "already running" if its supervisor is alive, deal with a PostgreSQL left running, write its own owner record, `pg_ctl start`, restore recovery (8.3), then the version checks (8.4). A `postmaster.pid` whose process still runs is stopped with `pg_ctl stop -m fast` only while this supervisor holds the lock, and only when the supervisor named in `supervisor.json` is gone (its pid not alive with that start time). Otherwise the start ends as "already running" and touches nothing [093]. lock.itest.ts starts two supervisors on aliased paths of one folder while the first runs a game, and its database keeps answering. Rules the randomized test holds over many event orders (start, quit, switch, port, profile change, a silent watcher, back up, restore, server crash, PostgreSQL crash, shell disconnect, supervisor killed at any step including an undo, a second supervisor starting, address change): never two app servers, never a restore while the server runs, never a backup during a restore, a killed restore always ends finished or undone on the next start with `raccoon` holding either the old or the restored data whole, PostgreSQL stopped whenever the supervisor exits normally, every request answered once, and a crash restarts the server after 1, 2, 4, 8 and 16 s, then error. Process deaths across real processes (Windows job objects, detached spawning) are proven by the smoke tests, not the fake-process test.

## 11. Build and release

**11.1 desktop.yml** [066][087]. Shaped like release-assets.yml, and called by image.yml as a new job after `release`, with the tag, once the GitHub Release exists. The calling job grants `contents: write`, `id-token: write` and `attestations: write`, and each job inside narrows them.
- **Release run** (called, or by hand with `tag`): checks out `refs/tags/<tag>` and nothing else, builds all five targets, signs, attests and uploads. It only adds: a release holding every desktop asset is left alone, one holding some is refused.
- **Dry run** (by hand with `ref`, a branch or SHA, and no `tag`): builds and smoke-tests all five targets from that ref, and its sign and upload jobs do not run (`if: inputs.tag != ''`), so nothing it makes can reach a release. This is how macOS is tested before the first desktop release, on the desktop work's ci/ branch.
- **Branch run** (`ci/**` pushes touching `desktop/**`, `desktop.yml`, `server/**`, `shared/**`, `db/**`, `package.json`, `pnpm-lock.yaml` or `pnpm-workspace.yaml`): the checks job, and the build and smoke test for Linux x64 and Windows x64, uploading nothing.
- **Checks job** (windows-2025, and ubuntu-24.04 on branch runs) [097]: installs the root and desktop packages and typechecks `desktop/tsconfig.electron.json`. On Linux it runs `pnpm test` whole. On Windows it runs `node --test` over `shared/`, `server/`, `client/` and `desktop/` unit tests only, since scripts/ and e2e/ unit tests check Linux CI tooling and spawn sh, docker or git. Both then run `pnpm test:int` against a throwaway cluster from the fetched PostgreSQL (`desktop/scripts/test-db.ts`, so the server's integration tests run on Windows for the first time), `pnpm test:desktop`, and the desktop e2e files (`node desktop/e2e/run.ts`, which runs `desktop/e2e/*.e2e.ts`: shell.e2e.ts and window.e2e.ts). macOS runs the same on release and dry runs. The Windows checks start as report-only (`continue-on-error`, failures listed in LOCAL-6's report) and become a gate once green, before the first desktop release. LOCAL-1 owns making server/ and shared/ pass on Windows, LOCAL-2 client/, LOCAL-3 and LOCAL-4 their own folders.
- macOS jobs run only on release and dry runs, never on a branch push [065].
- Every build and check job only reads. No step that runs pnpm or a package script has a token in its environment: `actions/checkout` keeps no credentials, and `GH_TOKEN` is set only on the fetch step (`node desktop/scripts/fetch-runtime.ts`, Node built-ins only), which runs before any install.

- **Round 1** made local pages send `referrer-policy: same-origin` and never allow `Origin: null`, after WebKit sent it on same-origin requests, with a WebKit job in CI to prove it. It also set the platform floors, gave PostgreSQL a free loopback port at each start, kept a VPN or public default route from becoming the share address, made the share origin follow changes without a reload, kept Electron imports in one folder so root CI needs no desktop packages, made installs wait for a clean stop on Windows, watched the Windows network profile, kept Domain networks off, and named the app RaccoonVTT.
- **Round 2** rebuilt the restore: it stops the server before any image is checked, builds into `raccoon_restoring`, swaps by two renames, drops a database only by name and tag, and picks every next-start action from a table of what the databases are. ## As built

Every place the build went its own way, with the reason, grouped by area.

**The contract**
- It also pins what the lanes share: the runtime folders (`desktop/.runtime/{node,postgres}` and the resources `node`, `postgres`, `app-server` and `licenses`), the server's file name `raccoonvtt-server[.exe]`, the supervisor's `--postgres <dir>` flag and the shell's `--smoke` and `--quit`. One place names each, so a lane cannot spell one differently.
- Headless status lines are one JSON `SupervisorStatus` each, and the smoke test drives a headless supervisor over the shell's own channel, so it tests the code the shell uses.
- The window's words gained what section 9 lacked, in its voice: "Rooms show here while RaccoonVTT runs.", "The backup failed: <reason>.", "The update failed: <reason>.", "Use a port from 1024 to 65535.", the footer "RaccoonVTT <version>", the singular quit line, the guard's confirmation and the Linux guard sentence. The window page added "Dismiss", "Loading rooms", "Loading backups", "RaccoonVTT did not answer. Try again.", "Before an update" for a backup with no target version, and a line on Backups while the database is down.
- The port runs from 1024 to 65535. `settings.json` keeps keys it does not know, so going back to an older version and forward again loses no setting.
- Every backup date shown is the backup's start. Network states read off, offline, public, domain, unknown and open.
- Server code may import the contract only with `import type`, since the image holds no `desktop/`, and a test enforces it. `import { type X }` counts as a value import because it still loads the module.
- `restore` answers once it starts, with a refusal at step 1 as a failure, and its end comes as a notice. `backupNow` answers when the backup ends.
- The desktop tsconfigs set `typeRoots` to the root's types, so Electron's `@types/node` never replaces Node 24's.

**The server in local mode**
- Interface names never shown to players also include Windows' friendly names (vEthernet, VMware, VirtualBox, ZeroTier, WireGuard, Wintun, TAP-Windows) and docker's `br-` and `veth`, since a computer with those would otherwise offer a virtual address first.
- The host-only guard runs in a route-level `onRequest` hook, so a create's JSON body is never parsed, and a refused import also sends `connection: close` so the body is not read on.
- A WebSocket upgrade that the 421 Host check refuses has its socket ended in that hook. The socket plugin's own hook ends refused upgrades but runs later and never sees the request, so each refused upgrade held a socket open.
- Host is matched lowercased and exactly, and Origin exactly, never through `new URL`, which turns `evil.example@localhost:P` into an allowed host. `::1` counts as this computer, while the peer filter admits only IPv4 loopback and private addresses, as section 6 lists.
- `csrfAllowed` takes a policy or a string, and a string still means one exact origin, so the hosted cases are unchanged. `main.ts` writes the 5 s status interval itself, because code outside `desktop/` may only `import type` the contract. A supervisor that dies during boot still stops the server: the channel is checked once the server listens, and nothing binds after.
- `buildApp` takes an optional `network` for tests and decorates `localNetwork` and `originPolicy` for the socket and room routes. The local part of `/api/config` is in `server/local/share.ts`.
- `passwordList` is exported and splits on CRLF or LF, since a checkout with Windows line ends failed the common-password test. Test child processes start from the environment Windows needs (`SystemRoot`, `TEMP`, `TMP`).
- Three `/api/config` assertions in the room integration tests gained `local: null`.

**The client**
- `useRoomConnection()` joined `client/state/view.ts`, since `useRoomView` throws outside a room and Home needs a read that does not.
- Access keeps a new DM link as a path and joins it to the share origin on each render, so an address change reaches a link already shown. The menu's Copy ends as a plain failure when both ways fail, since the join link is not shown there as text. Other surfaces select the text they show.
- `local-lan.e2e.ts` takes this computer's first private IPv4 as the network and skips with none. Home's two other-device states come from a routed `/api/config`, and a player moving a token and an address change with the tab open are not covered, but the switch off and on is, through a restart on the same port.
- Hook renders without a browser use a placeholder origin and no snapshot.

**The supervisor**
- The bundled PostgreSQL runs with `timezone = 'UTC'`, as the hosted image does. The integration tests on it failed two join request tests in a zone with summer time, where `now() + 180 days` lands an hour off.
- `postgres.log` (the `pg_ctl -l` file) rotates at 10 MB, 5 kept, before each start only, since `pg_ctl` holds it open while PostgreSQL runs. The other logs rotate as they write.
- The owner record and the guard record hold pid, start time and boot id. A guard's owner removes it by renaming it aside first, so the path is never an empty folder that another rename could take, and a macOS bind that races a contender's unlink fails with EEXIST and counts as taken.
- `pg_ctl stop` runs only for the postmaster this supervisor started, still running with the start reading it had then, or for one a start confirms: the program is `postgres`, and on Linux its working folder is this data folder (a postmaster works in its data folder), elsewhere it started when `postmaster.pid` says. A reused pid is never signalled. `postmaster.pid` goes only on evidence that nothing of this folder's runs as its pid: the pid is dead, the boot recorded beside it before its postmaster started (`raccoonvtt.boot`: Linux's `boot_id`, macOS's `kern.bootsessionuuid`, which no clock change moves) is not this boot, or the process is a known other program or runs as another user, each read from a source that needs no special rights (`/proc/<pid>/status`, `ps`, and on Windows `Win32_Process`). Anything else, a read the system refuses included, may be this folder's postmaster, so its `postmaster.pid` stays and the start stops with words. Windows has no boot id, so there the program's name carries it. Start readings no clock change moves (boot-relative ticks on Linux, `ps` in UTC on macOS) also go in the owner and guard records, with the same boot id. The 5 s watch checks the postmaster's pid alone, since a start time check costs a PowerShell run on Windows.
- `initdb` runs in a staging folder that gets the app's `pg_hba.conf` and settings and is flushed before it is renamed to `postgres/`, so `postgres/` means a whole cluster. A staging folder a cut-off init left is moved aside as `postgres.incomplete-<ms>` and never deleted. On Windows both renames try again for up to 30 s while another program, such as an antivirus scan, holds a file in the folder open. A damaged `secrets.json`, or a missing one beside `postgres/`, stops the start, since a new key would orphan every player link and a new password could never log in.
- On Windows the network profile of the network that carries the shown address decides, not any profile. The crash count is forgiven after 60 s up. A saved port that is still held is waited on for 5 s. A headless supervisor with no channel exits 1 on an error. A restore asked for during a backup waits for it. A restore that fails after the drop is finished in the same process by the next start's recovery.
- `listBackups` orders by the record's start, since two backups in one second otherwise sort by their random part. A backup this version cannot read is listed but gets no Restore button in the window.
- Test-only variables in `main.ts` (`RACCOONVTT_TEST_BUILD`, `RACCOONVTT_TEST_SERVER_ENTRY` and the `RESTORE_TEST_*` set) are read only by tests. `fetch-runtime.ts` has `--no-attestation` for working offline and writes `desktop/.runtime/runtime.json`.

There is no Vite Electron plugin: `vite.shell.config.ts` builds the main process and the preload as one CommonJS file each with their packages inside, so the app ships no `node_modules`. Electron 44 has no install script, so the workspace's allow list only denies electron-winstaller's.

- Quit from the tray and the app menu asks in a system message box while other devices are connected. The first-close notice shows once per user, kept in `shell.json` in Electron's profile, which Windows puts in `%LOCALAPPDATA%\RaccoonVTT\shell`. A new stop brings a hidden window back.

The upload job holds each signature and the provenance to the digest the sign job gave. A log line that cannot be written is dropped. A `restore.json` that does not read is deleted once the databases show nothing to recover. The window asks for its room list again when it comes forward or is shown, a first list that failed included, and on no timer, since each list runs the admin script, which sizes every room's history. The address shown to players skips libvirt, LXC, LXD, Podman, CNI and Parallels bridges, and keeps macOS's bridges: `bridge0` is the Thunderbolt Bridge, and `bridge100` and up serve Internet Sharing, whose devices may be the players. `local-lan.e2e.ts` fails instead of skipping with no network address in CI or a run that names WebKit.
- PostgreSQL's programs on Windows open every path through the ANSI code page (the language for non-Unicode programs), so under a profile named in a script that code page lacks, such as Cyrillic on a Western system, they could not open the data folder at all. PostgreSQL also names its shared memory after the data folder's path, case and all, and finds a dead postmaster's attached processes by that name, so the path it gets depends on the folder alone, the same at every start (D-261113-219).
- The folder is its canonical path, as the lock takes it (`fs.realpathSync.native`: junctions, symlinks, 8.3 names, subst drives, case and the `\\?\` prefix resolved), never the path the start was handed. The data folder's `postgres-link.json` for that canonical path is read first and its path handed on exactly. Without one, an ASCII canonical path is given as it is and nothing is recorded. Any other gets the junction `%ProgramData%\RaccoonVTT\<16 hex>\data`, the hex of a SHA-256 of this user's SID and the case-folded canonical path, recorded with its key. The code page is never asked about the data folder, so no reading, failed or changed, decides. The program folder is given by its path or its 8.3 short path only.
- A lost record finds the same junction: a folder of that name is used, and recorded again, only when Get-Acl shows this user owns it with exactly the app's ACL and its junction leads to this folder. Another user who made that name first can only stop the start. A recorded junction's folder that is gone is made again by its name. With a database and no record that reads, a missing folder stops the start, and the words say to put the record back from a copy. A record for another folder means the folder was moved or copied: Windows moves no folder a process works in, and a copy is another folder, so it gets its own junction. An earlier build's record (direct, short, or a folder of another name) still wins, and one that no longer leads to the folder stops a start whose folder holds a database.
- The installer runs `desktop/build/programdata.ps1` elevated. It makes `%ProgramData%\RaccoonVTT` with its security descriptor in one call: owned by Administrators, its ACL not inherited, SYSTEM and Administrators with full control, Users allowed only to list it, read its ACL and make folders in it (this folder only), and CREATOR OWNER with full control of what is made in it. A folder already there is kept only when its owner is Administrators or SYSTEM and its ACL is exactly that, entry by entry. Anything else by that name, an Administrators-owned folder with another ACL or a link included, is moved aside as `RaccoonVTT.untrusted-<ticks>` and a new one made, never mended in place, used or deleted. The uninstaller leaves it. desktop.yml's Windows jobs run the same script before the tests and the smoke test that run without the installer.
- The app makes its folder there through Windows PowerShell 5.1's `[System.IO.Directory]::CreateDirectory(path, security)`, which hands Windows the security descriptor at creation: owned by this user, by the SID read first, its ACL not inherited, full control for the user, SYSTEM and Administrators only. It checks first that RaccoonVTT's folder is the installer's, else the start stops with words to reinstall, and keeps the new folder only when Get-Acl reads it back exactly so, else the words name the cause. Only then does the folder get a random key, which no other user can read, and the junction, and the key is checked again before the record names the folder. A start with the record reuses the folder while it holds that key and its junction leads to the data folder, with no PowerShell.
